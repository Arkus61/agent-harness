## 2. Существенные противоречия и решения

### C01. Разные языки и способ поставки

**Где:** D4, начало и §18.2: Python/Pydantic/asyncio; D1/D2/D5/D6: интерфейсы и структура на TypeScript; D3 содержит Python API.

TypeScript-примеры сами по себе не доказывают утверждённый язык, но при буквальной реализации получится несколько сред запуска. Последующее требование пользователя — быстрый локальный и кроссплатформенный продукт.

**Решение:** Rust stable, Tokio, Serde, SQLite со встроенной библиотекой, нативный CLI. Доменные контракты переносятся по смыслу. Скрипты конкретного проекта могут использовать другие языки; ядро от них не зависит. Отдельные release-сборки Windows/macOS/Linux. Измерять скорость ядра, модели и сборок отдельно; Rust не объявляется доказательством ускорения всей задачи.

### C02. SQLite против PostgreSQL и нескольких серверных продуктов

**Где:** D3 §§3–5 и MVP требуют PostgreSQL; D7 §3 требует PostgreSQL/pgvector; D4 §§3.2,10.1 выбирает SQLite; D6 §33 добавляет Beads/MEX/Hindsight.

**Решение:** для локальной версии одна управляющая SQLite с WAL, FTS5 и таблицами рёбер, отдельный каталог объектов. Графовые обходы ограничены и выполняются Rust-кодом либо рекурсивными запросами. Векторы — отдельный факультативный индекс. PostgreSQL нужен при удалённых исполнителях, нескольких управляющих писателях или измеренном ограничении локальной схемы. Семантические API остаются прежними, но перенос базы требует миграции, а не простой смены строки подключения.

### C03. Несколько источников истины

**Где:** D6 §§2.1,6,13,33 распределяет авторитетное состояние между Event Log, Beads, Working State и другими stores; D1 имеет собственный State Store; D3 разделяет canonical Git и metadata DB.

**Решение:** события, версии постановки, проверки, задачи и проекции управления записывает один координатор в одной SQLite-транзакции. Проекция Task DAG не является второй независимо изменяемой истиной. Код — Git; большие данные — объекты по хешу; curated ADR/документы проекта — Git; индекс — производный. Beads в локальном MVP не управляет задачами; будущий мост имеет явно назначенного владельца записи.

### C04. Worktree, процесс и sandbox смешаны

**Где:** D1 §2.1, D5 §§13,32, D8 §7 называют worktree изоляцией; D4 §13.2 требует контейнер; D6 §11 предлагает subprocess/tmux/docker.

**Решение:** worktree разделяет код; асинхронная сессия разделяет контекст; supervisor управляет процессами; sandbox обеспечивает только проверенные ограничения. `native-trusted` — быстрые команды с правами пользователя. `isolated` — профиль с доступными файловыми/сетевыми ограничениями. Job Objects и Unix process groups не объявляются одинаковым механизмом безопасности. Требуемая изоляция не заменяется native при её отсутствии. `tmux` не входит в обязательную поставку Windows.

### C05. Одноагентный пилот против обязательных подагентов

**Где:** D4 §3.2 и §5.3 допускает одного worker; D1/D6 требуют параллельный граф.

**Решение:** один агент — первый вертикальный этап, а завершённый MVP включает минимум два взаимосвязанных исполнителя, интеграцию, независимую приёмку и адресное исправление. Сессии агентов живут в одном координаторе; процессы нужны командам. Скорость не достигается запуском нового интерпретатора для каждой роли.

### C06. Jev обязателен или отложен

**Где:** D4, уточнение и §14.0, фиксирует обязательные три применения: модели, tools/skills, риск; D6 относит typed inference к P1; D8 делает его стартовым P0.

**Решение:** DecisionService, question registry, журнал и три точки интеграции входят в основу. Нейронный backend сначала подключается в наблюдательном режиме и оценивается. Затем включаются маршрутизация и предусмотренные политикой семантические остановки. До включения существуют программные ограничения и ограниченный fallback. Целевая архитектура содержит Jev-подобный нейронный backend; он не обязан быть конкретным облачным API Jev.

Это уточняет прежний ответ в текущей сессии: после чтения D4 слой решений больше нельзя считать просто необязательным будущим расширением.

### C07. Семантический score начинает выдавать права

**Где:** D8 §§10,20,23 показывает `risk < threshold → allow`, `confidence > 0.90 → auto execute` и merge по `spec_compliance`; D8 §36 и D4 §§4,14.0 запрещают выдачу прав моделью.

**Решение:** `DecisionAssessment` — только сигнал. PolicyEngine проверяет действующие grants; высокий score не расширяет их. Assessment связан с хешами действия, ресурсов, grants, backend и вопросов. `UNKNOWN`, неполный ввод и timeout не равны low risk. MergeGate читает реальные применимые отчёты. Модель может повысить строгость, предложить probe или другой маршрут; не может отменить запрет.

### C08. Дублируются маршрутизаторы

**Где:** D2 Routing/Risk Engine; D8 Task/Model/Agent Router; D7 SkillRetriever/PathScorer; D5 Decision Engine; D6 Decision Engine.

**Решение:** общий DecisionService предоставляет typed inference и не исполняет действия. ModelRouter выбирает модель, ContextPlanner способ извлечения, SkillResolver процедуры, StrategySelector стратегию; все используют одну версию правил и общий бюджет. Они не создают свои независимые runtime, journals и разрешения. Если существенный запрос маршрутизатор изменил, новая каноническая операция заново проходит policy/risk.

### C09. Два планировщика альтернатив

**Где:** D5 SESE; D7 PathPlanner/Scorer/DagCompiler; D2 §14 выбирает решение Frontier Judge.

**Решение:** SESE отвечает за альтернативные стратегии решения задачи. Skill Graph выдаёт допустимые версии процедур и ограничения их композиции. Их предложения пути передаются одному StrategySelector и одному DagCompiler. Модель сравнивает содержательные качества; программный код применяет ограничения и фиксирует выбранный план.

### C10. Число кандидатов и цена поиска

**Где:** D4 §11: цель три; D7 §4.4: один–два; D5 FAST: три, STANDARD: 5–8, algorithm v1: шесть, MVP: пять.

**Решение:** SIMPLE — один путь с причиной; STANDARD — цель 2–3 существенно разных описания и probes максимум двух; DEEP — расширенный лимит только в отдельном профиле. Обязательное рассмотрение альтернатив для рискованной/неоднозначной задачи имеет проверяемое исключение. Независимость контекста не требует обязательной параллельной полной реализации всех вариантов.

### C11. Права зависят от класса модели

**Где:** D2 §15.1 запрещает cheap worker писать main, но делает `frontier.main_worktree` настраиваемым. §19 разрешает secret локальному worker по одному признаку локальности.

**Решение:** любой builder меняет только свою разрешённую среду. Доступ определяется ролью, операцией, областью и grants, а не ценой модели. Локальность не выдаёт право читать секрет. Право доступа к данным и право отправки backend проверяются отдельно до вызова.

### C12. Кто проходит независимую проверку

**Где:** D1 §§2.5,16,27: security условный, но §42 включает его в обязательных reviewers; D8 §8 делает Spec Compliance опциональным; D6 §36 P0 не включает security-agent.

**Решение:** для каждого кандидата результата кода обязательны детерминированные проверки, соответствие требованиям, review кода, проверка тестов и компактный независимый security-проход. Чувствительные изменения добавляют глубокую security-проверку. Интеграционный профиль обязателен при нескольких ветках. Неизвестная классификация не снимает обязательную проверку.

### C13. Недостаточная независимость проверяющих

**Где:** D1 §2.2 запрещает полный диалог; D4 §5.2 допускает логи Builder; D3 §§24–26 предлагает общую память.

**Решение:** reviewer видит исходную постановку, закреплённые критерии, код кандидата, точные результаты доверенного runner и curated контекст. История автора, его самооценка и свежие непроверенные conclusions исключаются. Сырые tool traces допустимы как факты. Общая память фильтруется по происхождению и времени; сведения, созданные текущим builder, не используются как независимое подтверждение.

### C14. Повторное ревью после исправления

**Где:** D1 §29 предлагает selective review; D4 §12 и D6 §§12.2,23 связывают proof с точным состоянием.

**Решение:** исправление создаёт новый VerificationCandidate, все обязательные gates в MVP запускаются заново. Позже возможен reuse только при полном манифесте входов конкретного check и доказанной области влияния. Экономия вызовов не оправдывает старый PASS для новых файлов.

### C15. Неопределённые статусы и «skip»

**Где:** D6 §21 имеет pass/fail/skip; D1 использует PASS/PARTIAL/REJECT; D4 использует pass/fail/unknown и BLOCKED вместо FAILED.

**Решение:** отдельно фиксируются состояния Run, TaskNode, Attempt, Action, Check и Publication. Для check: NOT_RUN/RUNNING/PASS/FAIL/ERROR/INCONCLUSIVE/NOT_APPLICABLE. Последнее разрешает только политика для условной проверки; обязательный check не может быть «пропущен и засчитан». Частичное покрытие требований не подтверждает завершение. VERIFIED и MERGED — разные статусы.

### C16. Порядок объединения и ревью

**Где:** D1 проверяет после интеграции; D6 lifecycle сначала review отдельных веток, потом integration и final verify; D8 FSM помещает VERIFYING перед INTEGRATING.

**Решение:** локальные проверки являются обратной связью. Итоговые независимые reviews и Gate относятся к уже объединённому неизменяемому кандидату. У каждой попытки фиксируются input_base_sha/output_sha; интеграция переносит только собственную delta, а не историю с включёнными зависимостями. Repair начинается от отклонённого объединённого кандидата.

### C17. Неатомарная запись между Git, файлами и БД

**Где:** D3 §7: Git Commit + Index Update; D7 §3.3: транзакционная публикация manifest, связей, embeddings и scan; D6 §33 допускает DB либо JSONL.

**Решение:** объект записывается и долговечно публикуется по хешу до транзакции с метаданными. В SQLite атомарны событие, проекция и исходящая работа. Git-export и индексы — возобновляемые производные операции. Отсутствующие обязательные объекты блокируют приёмку; осиротевшие удаляются после сверки ссылок. Экспорт JSONL не становится вторым писателем журнала.

### C18. Журнал не обеспечивает однократность внешнего эффекта

**Где:** D1 §§31–32 и D6 §§27,35 кратко обещают recovery; D4 §7 уже описывает unknown effect.

**Решение:** записать ActionIntent до эффекта, после — Receipt. Разрыв требует reconciliation; новое исполнение не следует из одного отсутствия receipt. Допуск попытки блокирует принятие старых результатов; supervisor останавливает процессы отдельно. Replay восстанавливает проекции и сохранённые ответы, не делает внешние операции заново.

### C19. Хуки вызывают дубликаты и бесконечные циклы

**Где:** D1 §26, D8 §26 и D7 §5.3 задают много событий без единого барьера проверки.

**Решение:** транзакционная исходящая очередь, повторная доставка и идемпотентные обработчики. Один verification batch на кандидата, один repair batch на его поколение, ограничение циклов. Несколько FAIL разных reviewers агрегируются. Позднее событие старого поколения не меняет текущее. Провал детерминированной фазы закрывает batch без ожидания не запущенных reviewers.

### C20. Доверие к знанию подменяет право задавать инструкции

**Где:** D3 §11 предлагает общую иерархию trust, где PROJECT_VERIFIED выше USER_PROVIDED; D4 §8.4 разделяет authority/trust/confidentiality.

**Решение:** независимые поля: authority, verification_status, provenance, confidentiality, applicability. Проверенный старый факт не отменяет новое указание владельца. Сводка и embeddings не повышают authority. При конфликте сохраняются оба утверждения и условия; проверяется текущий первоисточник.

### C21. «Источник существует» не означает «вывод доказан»

**Где:** D2 §§9–10,17 проверяет hashes/ranges/excerpts; D5 §16 даёт иерархию evidence; D8 §19 включает численный tests_pass.

**Решение:** отдельно структурная проверка ссылки, содержательная поддержка claim и фактический outcome. Hash подтверждает идентичность объекта, не истинность вывода. Тест подтверждает конкретный сценарий, не отсутствие всех дефектов. Метрики содержат единицы, метод, среду, число измерений и неопределённость; сырые model scores не становятся вероятностью корректности.

### C22. DAG содержит fallback и repair, которые могут создать цикл

**Где:** D7 §§4.6,5.2 добавляет fallback branch и локальное перепланирование; D5 имеет Solution Graph; D6 — Task Graph и Skill Graph.

**Решение:** различаем Skill Graph, Solution Search Graph, Execution DAG и граф зависимостей свидетельств. В Execution DAG нет циклов. Repair и переключение стратегии создают новую ревизию плана; они связаны событиями FSM, а не обратным ребром внутри старого DAG. Циклы ALTERNATIVE_TO допустимы только в библиотеке и обходятся с пределами.

### C23. Слишком поздние безопасность и измерения

**Где:** D6 §35 ставит policy/security в Phase 7 и telemetry/eval в Phase 8, хотя оба нужны P0; D5 Phase 2 добавляет Evidence Store, используемый MVP; D3 переносит conflict detection после базовой памяти, хотя DoD требует её.

**Решение:** policy, доказательства, журнал, basic tracing, диагностирование конфликтов и независимая приёмка присутствуют в первом исполняемом цикле. Расширенные UI, статистика и глубокие специализированные проверки приходят позже. Статус MVP определяется целым работающим процессом, не количеством интерфейсов.

### C24. Расширения могут обойти ядро

**Где:** D6 «everything-is-a-plugin» и overrides; D7 скиллы со скриптами; D2 host hook adapters.

**Решение:** P0 — встроенные адаптеры и типизированные интерфейсы. Недоверенные native-библиотеки не загружаются в управляющий процесс. Скрипт навыка выполняется через Gateway/Runner. Overrides могут сузить grants, но не расширить политику владельца. Привязка к Codex/Claude/Cursor — факультативный транспортный адаптер, не обязательная часть собственного ядра.

### C25. Ускорение превращается в неограниченный параллелизм

**Где:** D1/D5/D6 дают разные max_parallel_agents; D8 предлагает fan-out по файлам; D2 считает главным выигрыш token savings.

**Решение:** отдельные лимиты LLM, процессов, дискового обхода, проверок и локальной GPU; ограниченные очереди. Сначала детерминированное сужение, потом ограниченная семантическая оценка. Прогреваем инструменты и неизменяемые зависимости, а не общую изменяемую среду. Основной показатель — стоимость и время принятого результата с сохранённым качеством.

## 3. Положение сторонних проектов

Матрица D6 полезна как перечень идей. Для локального MVP предложены архитектурные заимствования, а не установка всех framework:

- Beads, HAR, Gas City — источники принципов графа, worktree, supervisor; соответствующие функции собственного ядра.
- MEX/Hindsight — возможные будущие провайдеры знаний/опыта после проверки хранения, приватности и требований к установке.
- Serena/LSP/tree-sitter — добавление структурного поиска после lexical baseline; Python-служба не становится обязательным runtime ядра.
- Promptfoo — факультативный offline-инструмент; приёмочные инварианты ядра проверяются также без него.
- Invariant — возможный adapter; policy enforcement и sandbox не передаются единственному стороннему компоненту.
- Phoenix/OTLP — факультативный наблюдающий backend; его отказ не меняет корректность исполнения.
- Jev либо локальная модель — заменяемый обязательный по назначению DecisionProvider, конкретная реализация выбирается измерением.

Лицензии, актуальные API, доступность бинарных сборок и поддержка ОС проверяются до реального подключения. Слова «verified» внутри исходного документа не являются проверкой, выполненной в этом сравнении.

## 4. Итог решения

Общее ядро: Rust/Tokio + одна SQLite + хранилище объектов + Git + платформенный supervisor.
